# 行为检查

用用户能观察到的结果组织测试。例如筛选更新后列表改变且后退恢复原筛选，比测试内部 state 字段更稳定。选择最靠近真实风险的层次：纯计算用单元测试，组件交互用组件测试，导航与跨界面路径按需要做浏览器检查。

行为变化时新增或更新相关测试，覆盖变化结果和重要保留行为；没有行为变化的纯说明或格式修订不强写镜像测试。对表单或异步页面，重点检查正常成功、服务器拒绝、响应延迟或乱序、空结果、重复操作和恢复。不是每次都跑全部组合；说明哪些与当前变化有关。复现缺陷的测试应在修复前暴露问题、修复后证明可观察行为恢复。

键盘检查走完整操作路径，观察焦点进入、关闭后返回、可见性和错误定位。核对控件标签及阅读顺序；自动扫描无法证明完整键盘或辅助技术行为。没有实际读屏测试就不能声称已通过读屏验证。

浏览器与视口选择来自项目支持范围和变动特征；有实际渲染证据才能比较布局。区分自动化浏览器、人工操作和静态检查，保留执行环境、关键输入、验收对应、实际方法与结果；未覆盖浏览器、视口或辅助技术说明原因和影响。留存的验证说明、截图及证据附件统一放在业务仓库 `docs/frontend-developer/` 下，可按功能分组；测试代码及断言快照保留工程测试目录。测试夹具使用合成内容，不把真实用户数据写入截图或快照。

偶发失败先记录条件和重现情况，检查异步等待、资源清理及环境因素；不要任意延长等待、弱化断言或移除用例来获得绿色结果。

延伸阅读：[Testing Library 指导原则](https://testing-library.com/docs/guiding-principles/)。只借鉴行为测试思路，不要求更换项目测试工具。
