# Phase 1 — PLAN：规划改动

**输入：**请求或验收、相关项目代码、已确认设计/技术约定与真实契约。

**输出：**可独立实施的范围、受影响路径、保留行为、顺序、检查安排及未决依赖；需要持久依据时保存计划。

执行前读取 [职责与授权边界](../sprite-frontend-developer-ui/references/boundaries.md)，沿用已有决定和授权；本阶段可单独运行，共享参考随安装保留，不要求先执行其他阶段。
所需入口或共享参考缺失时，从 [本角色仓库](https://github.com/ai-sprites/frontend-developer) 的同一明确版本补齐完整目录，保留自定义；取不到则说明缺项，继续有依据的独立部分。

## 1. 核对来源与实际影响

读取当前请求、已确认设计与验收、项目 README、相关页面、组件、契约和测试，保留来源与实际版本。按 [本职工作方法](../sprite-frontend-developer-ui/references/workflow.md) 核对适用技术约定与本职选型；现有依据足够就继续，不要求补完整 PRD、其他角色或单独技术档案。

列出本次可观察结果和须保留的行为，定位受影响路由、组件、样式、数据请求、测试与客户端配置。评审任务到这里区分事实、建议与待决定项，不能把建议当成已批准要求。

## 2. 划出最小完整改动

布局任务读 [复用与布局](../sprite-frontend-developer-ui/references/reuse-layout.md)，表单或异步交互读 [状态与表单](../sprite-frontend-developer-ui/references/states-forms.md)。查看真实组件 API 与资产，明确 URL、服务端数据、输入和临时 UI 状态的归属，列出加载、刷新、空数据、失败、恢复和重复操作的相关分支。

核对支持浏览器、视口、键盘/焦点、辅助技术、国际化与性能影响。接口资源、HTTP 状态、返回结构、分页及权威 OpenAPI YAML 以真实主源为准；不猜字段，不为方便页面顺带改造后端。对尚未确定的服务能力单列依赖，已明确的布局和校验可继续。

## 3. 安排实施与验证

把需求或风险对应到拟修改区域与可观察检查，选项目已有单元、组件、浏览器和静态检查入口。视觉改动安排实际渲染，辅助技术证据按实际可用条件安排，不以自动扫描代替键盘或读屏。

先处理真实依赖，再安排可独立修改的文件。多人编辑共享契约、公共库、根配置、CI 或公共测试前明确单一编辑者和交接顺序；沿用已有分工，不强设总负责人。

## 4. 形成可交接的实施依据

复杂、多步骤、有风险或跨重要区域/仓库且需要持久依据时，读取完整 [实施计划模板](../sprite-frontend-developer-ui/assets/templates/implementation-plan.md)；有排序、并行或验收追踪价值才用 [任务模板](../sprite-frontend-developer-ui/assets/templates/implementation-tasks.md)。按 [交付与留存](../sprite-frontend-developer-ui/references/delivery.md) 填写适用内容，小改动可在回复或已有说明记录。

写清目标、受影响路径、须保留行为、顺序、契约协调、检查方法及风险决定。需人的决定按职责边界核对来源、具体提问，沿用已有答案与授权；未答事项保留来源和受影响部分，不阻碍独立工作。已有计划局部更新，并说明旧结论哪些仍适用。

## 完成条件与下一阶段

- 目标、来源与实际版本、改动范围和重要保留行为明确。
- 顺序、共享文件分工（若有）、验收检查及未决依赖可独立交接。
- 只保存有用途的计划/任务，决定与旧依据的变化已写回。

完整开发任务继续 [Implement](../sprite-frontend-developer-implement/SKILL.md)；用户只要求方案或影响分析时交付依据与缺口，在此结束。
