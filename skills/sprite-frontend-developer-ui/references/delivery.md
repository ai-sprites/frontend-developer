# 交付与留存

## 选择完整模板

开发范围填写 `frontend` 或本次明确扩展的实际范围。模板安装不等于必须生成全部业务文档。

| 模板 | 何时使用 | 填成什么 |
|---|---|---|
| [实施计划](../assets/templates/implementation-plan.md) | 复杂、多步骤、有风险或跨重要区域/仓库，需要持久实施依据时，在改动前读取 | 目标、保留行为、实施顺序、仓库变更、验收、契约协调及风险决定 |
| [实施任务](../assets/templates/implementation-tasks.md) | 清单能改善排序、并行分工或验收覆盖时读取 | 可执行任务、依赖、负责人分工相关信息与实际证据/阻碍 |
| [实施说明](../assets/templates/implementation-notes.md) | 功能完成或受阻后需要交接时读取；简单小改动可在回复中覆盖适用内容 | 真实状态、变更及原因、采用决定、精确检查结果、限制、覆盖和后续验证 |

读取选中的完整模板后再填充；保留原章节和字段，填入真实业务信息。已有文档结构可继续沿用，但须覆盖模板中的适用内容；无关字段写无或不适用，不编造数据、负责人、批准或执行结果。Markdown 占位链接采用 `(<...>)`；业务产物中的链接必须替换为真实路径，不保留模板路径作为交付地址。

需要的工作模板或引用缺失时，从 [本角色仓库](https://github.com/ai-sprites/frontend-developer) 的同一明确版本补齐完整 Skill（包括 `SKILL.md`、`references/` 与 `assets/`），保留用户自定义；不要编造简版冒充原模板。无法补齐时说明缺失与限制，继续有充分依据的独立部分。

## 实现交付

实现或修复任务交付实际代码、相应测试和清楚的实现说明。完整功能、跨模块改动或需要交接时，读取完整实施说明模板，把适用字段填入业务仓库 `docs/frontend-developer/` 下的实施说明；有对应记录就按下述迁移规则局部更新。PR 链接已落盘的说明；小改动可直接在回复中说明，不另建记录。说明应讲清：

- 完成了什么、依据是什么、还缺什么；有阻碍时说明影响和下一步，不要求填写固定状态或负责人表。
- 改了哪些行为和文件、为什么改，哪些旧行为需要保留；已有相关计划直接链接；没有计划或任务清单就写无，不为填链接新造文件。
- 使用的已确认技术约束、设计决定、ADR、项目模式及本次技术选择和简短理由；写入当前说明即可，不另建选型档案。
- 需求或验收项对应的实现与检查、精确命令或操作及实际结果；未运行检查、原因和受影响结论。
- 已知限制、风险和问题（没有则注明无），仍需验证的具体行为、路径及下一步。实现成功、测试通过和已经发布分别依据实际证据判断。

一份已有说明能讲清的，不拆成计划、任务、实现和验证四份文档；实际改动、测试结果和必要风险不能省。

## 验证记录

以验收或用户行为对应检查，交付前端验证结论；功能验证、回归或正式验收把验证记录保存到业务仓库 `docs/frontend-developer/`，一次简单检查可在当前回复记录。至少说明被测版本、浏览器/视口与环境、关键输入、风险和验收来源、精确命令/操作、逐项结果及证据、问题复现、未覆盖及原因、残余风险，以及通过/失败/阻碍的总体判定和成立范围。静态检查、实际渲染、键盘操作与读屏结果分别陈述，未做的不能冒充完成。

按上述交付要求保存业务记录时，把结论、验证证据及附件写入业务仓库 `docs/frontend-developer/`，例如 `docs/frontend-developer/<feature-id>/frontend-verification.md`。已有本职产物散落在其他位置时，先读取并保留有效内容，再迁入 `docs/frontend-developer/`，同步文内链接、其他引用及已有索引；遇到同名文件先比较并合并，避免覆盖用户内容。交付所属仓库、根目录相对路径、真实链接与版本。可选索引用 `kind: "verification"` 和根目录相对 `path` 登记，附件单独列出，Markdown 链接相对文档；源码、测试、迁移、配置及构建输出保持工程原生目录；角色和 Skill 安装资源保持客户端目录。读取上游资料按真实来源路径，资料 host repo、版本和文件由用户指定或沿用项目明确约定，未提交或未推送如实说明；bridge 不替上游推送。

## 产物留存与交接

首次引入角色或实践时，整次接入只把未明确的资料 host repo 和产物业务仓库合并询问一次，允许“暂无/稍后配置”并先完成接入；已指定角色、已答或已暂缓的项不重问，真正读取时再补必需版本、功能或文件。

按上述交付要求留存实现说明和验证证据时，把前端实现说明与验证结果实际写入业务仓库 `docs/frontend-developer/`，例如 `docs/frontend-developer/<feature-id>/frontend.md`；实施计划、任务清单、实现说明、验证证据和附件均归本角色目录，需要时在其下按功能分组。已有本职产物散落在其他位置时，先读取并保留有效内容，再迁入 `docs/frontend-developer/`，同步文内链接、其他引用及已有索引；遇到同名文件先比较并合并，避免覆盖用户内容。源码、测试、迁移、配置及构建输出保持工程原生目录；角色和 Skill 安装资源保持客户端目录。交付真实链接、所属仓库、相对 Git 根的路径及依据版本；不能落盘就明确说明。

资料 host repo、版本及功能或文件由用户指定，已有明确项目约定就沿用；读取上游资料按真实来源路径，不要求搬入本角色目录。可选 `artifacts.json` 用 `features[功能标识].documents` 登记 `kind: "implementation"` 与根目录相对 `path`，或外部 `url`；附件单独列出，Markdown 链接相对文档。不要求凑齐角色或索引。跨 Git 消费前核对文件已进入可获取提交，未提交/推送如实说明；bridge 不替上游写入或推送。

项目已有资料索引时，创建、更新、移动或删除本职产物后同步其真实链接和简要说明，移除失效条目，只登记确实存在的文件；使用相对索引的链接。外部资料保留主源及实际版本，不将链接可达或同一提交当成内容已经一致或获批。没有索引时不为本角色强建全局登记。

当前任务确需跨 Git 读取、固定版本、比较或导出留存时，复用已有 bridge；缺失或能力不足时，AI 按 [artifact-bridge README 与接入手册](https://github.com/ai-sprites/artifact-bridge)把同一明确版本的完整 Skill 补齐到当前客户端已有目录，保留自定义并告知用户，无需再单独确认安装。用户拒绝安装或权限、网络不足时说明限制，继续可独立部分。普通本地文件和纯角色安装不触发补齐。
